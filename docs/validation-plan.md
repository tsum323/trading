# План валидации

Правила проверки любых стратегий. Цель — не найти прибыльную стратегию, а
не обмануть себя. Результат, полученный с нарушением этих правил, считается
недействительным.

## 1. Данные

- Только реальные публичные данные биржи, сохранённые в `storage.candles`
  с указанием `source` и `fetched_at`. Синтетика допустима лишь в юнит-тестах.
- Перед тестом ряд проходит `validateSeries`: пропуски фиксируются в отчёте и
  **не заполняются**. Решение, требующее свечей из пропуска, не принимается.
- Используются только закрытые свечи (`closeTime <= decisionTime`).
- Учитывается смещение выживших: набор символов фиксируется заранее, не по
  текущему топу капитализации.

## 2. Разбиение истории

Хронологическое, без перемешивания:

| Часть | Доля | Назначение |
|---|---|---|
| Исследовательская (in-sample) | первые 60% | разработка правил, подбор параметров |
| Валидационная | следующие 20% | выбор среди ограниченного числа кандидатов |
| Отложенная (holdout) | последние 20% | **однократная** финальная проверка |

Отложенная выборка запускается один раз на зафиксированной версии стратегии.
Повторный запуск после изменения правил переводит её в разряд
исследовательской, и нужна новая отложенная выборка (более свежие данные или
перспективный тест).

Дополнительно — walk-forward: окна обучения 3 месяца / проверки 1 месяц со
сдвигом 1 месяц; отчёт приводит результаты каждого окна отдельно.

## 3. Модель исполнения (гипотетическая)

- Вход — `open` свечи, следующей за `basisCloseTime`. Никогда не по `close`
  опорной свечи.
- Комиссия и проскальзывание по `strategy-spec.md` §5, на каждой стороне.
- Если в одной свече затронуты и стоп, и цель — исход `ambiguous`, в
  статистике считается как стоп.
- Гэп через стоп — исполнение по `open` свечи, а не по уровню стопа.
- Сигнал, вход которого попадает в пропуск данных, — `no-entry`, исключается
  с подсчётом в отчёте.
- Оценщик исходов версионируется (`evaluator_version`); смена логики
  оценки требует пересчёта всех исходов.

## 4. Метрики

Для каждой версии стратегии отдельно (сигналы разных версий не смешиваются):

- число сделок, доля `ambiguous` и `no-entry`;
- матожидание в R после издержек и его 95% бутстреп-интервал (блоковый
  бутстреп по дням, чтобы учесть автокорреляцию);
- profit factor, доля прибыльных, средний выигрыш/проигрыш в R;
- максимальная просадка в R и длительность просадки;
- распределение по символам, месяцам, часам суток, направлениям;
- MFE/MAE в R;
- **базовая линия**: ≥1000 прогонов случайных входов с той же частотой,
  направлением, стопом, целью и истечением; результат стратегии сравнивается
  с перцентилями этого распределения.

## 5. Множественные проверки

- Каждый прогон (параметры, период, версия кода, результат) записывается в
  журнал исследований, включая неудачные. Отчёт приводит общее число
  испробованных конфигураций.
- Число кандидатов, переходящих на валидационную выборку, — не больше 5.
- При большом числе испытаний применяется поправка (Bonferroni или deflated
  Sharpe ratio); без неё результат помечается как «разведочный».

## 6. Перспективный тест (forward / paper)

- Стратегия фиксированной версии работает на живых публичных данных.
  Сигнал записывается в `signals` с `mode = 'live'` в момент формирования;
  `recorded_at - created_at` должно быть не больше одного таймфрейма, иначе
  сигнал помечается как запоздалый и исключается.
- Сигналы неизменяемы; исход вычисляется только после `expiresAt` или
  срабатывания стопа/цели.
- Минимальная длительность — 8 недель и не менее 50 сигналов; до этого
  результат «не определён».
- Расхождение live с replay на том же периоде (сигналы реплея по тем же
  свечам) — признак ошибки; расследуется до продолжения.

### Реализация

`.github/workflows/live.yml` каждые 15 минут запускает `npm run live`
(`services/live-cycle.ts`). Данные хранятся в ветке `data` текстом
(`FileArchive`): свечи — CSV по месяцам, сигналы и исходы — журналы JSONL,
которые только дописываются. Каждая запись сигнала содержит `recordedAt`,
коммит кода (`codeCommit`) и флаг `late`; история коммитов ветки `data`
дополнительно подтверждает время записи.

- Первый запуск только загружает историю для прогрева; сигналы формируются
  лишь для свечей, закрывшихся после предыдущего цикла (иначе это реплей).
- Пропущенные запуски догоняются: свечи догружаются, сигналы за пропущенное
  время записываются с `late: true` и в статистику не входят.
- Планировщик GitHub Actions может задерживать запуски на минуты и дольше;
  доля запоздалых сигналов видна в отчёте `reports/trend-pullback.md`.

## 7. Обязательные автоматические тесты

Запускаются в CI (`npm test`) и блокируют слияние:

1. Срез по времени: граница `closeTime == asOf` включительно, `asOf - 1` —
   нет; флаг `isClosed` не учитывается (`closed-candles.test.ts`).
2. Реплей: стратегия не видит свечей с `closeTime > decisionTime`; нет
   решений на незакрытой свече; искажение будущего не меняет прошлые
   сигналы; подлог `basisCloseTime` → `LookaheadError` (`replay.test.ts`).
3. Каждый индикатор проходит `expectCausal` (`src/test/causality.ts`).
4. Каждая стратегия проходит тест инвариантности к будущему из `replay.test.ts`
   на своих данных.
5. Хранилище: закрытая свеча не перезаписывается; сигнал не перезаписывается;
   `basis_close_time <= created_at` (`sqlite-store.test.ts`).
6. Оценщик исходов (`backtest/outcome.test.ts`): вход строго по `open`
   свечи после `basisCloseTime`; свечи до входа и после выхода не влияют на
   результат; свечи, закрытые после `asOf`, не используются (`pending`);
   правило `ambiguous`; гэп через стоп — по `open`, через цель — по цели;
   пропуск во время сделки — `data-gap`; издержки входят в R.

## 8. Отчёт

Каждый отчёт содержит: версию стратегии и коммит, период и источник данных,
пропуски, число испробованных конфигураций, метрики §4 с интервалами,
сравнение с базовой линией и явную формулировку: подтверждена ли гипотеза,
отвергнута или результат не определён. Формулировки «стратегия прибыльна»
без выполнения §2–§6 не допускаются.
